# 09c.1 — Integration Testing en ASP.NET Core

Lectura secundaria y opcional de [Lab09c](../README.md). El README contiene lo necesario para ejecutar y comprender los tests.

## Qué entendemos por integration test

Comprobamos que varias piezas reales trabajan juntas dentro de una frontera elegida. Aquí enviamos una request a la aplicación y observamos su respuesta HTTP: routing, middleware, Controller, DI, Service, model binding/validation y serialización participan realmente.

En Lab09b llamábamos al service directamente e inyectábamos un repository controlado por Moq. Eso permitía estudiar reglas y efectos del service con aislamiento. Aquí también detectamos problemas que ese test no puede encontrar: una ruta equivocada, un registro DI faltante o un resultado HTTP/JSON incorrecto. Los dos alcances se complementan.

## WebApplicationFactory, TestServer y HttpClient

`WebApplicationFactory<Program>` prepara y arranca el host de la aplicación usando su punto de entrada. Gestiona `TestServer`, los clients y su liberación. `CreateClient()` permite empezar a enviar requests sin ejecutar manualmente `dotnet run`.

**TestServer** es el servidor de pruebas de ASP.NET Core en memoria. Ejecuta el pipeline real, pero no necesita abrir un puerto TCP como Kestrel. **HttpClient** construye las requests, envía JSON y recibe status, headers y body a través del transporte proporcionado por TestServer. No estamos mockeando el Controller ni llamando directamente a sus métodos.

```text
WebApplicationFactory<Program>
          ↓ arranca/configura
Host ASP.NET Core + TestServer
          ↑ requests/responses
       HttpClient
          ↑
         Test
```

El punto de entrada generado mediante top-level statements se expone con `public partial class Program { }` para poder referenciarlo desde el proyecto de tests. `Microsoft.AspNetCore.Mvc.Testing` aporta la factory y la infraestructura de arranque; se instala solamente en tests.

## Qué integramos y qué queda fuera

| Dentro de esta prueba | Fuera del alcance actual |
| --- | --- |
| Registro DI y construcción del Controller con el Service real | Base de datos, SQL y persistencia entre reinicios |
| Routing y middleware de la aplicación | Kestrel, sockets TCP, proxies, TLS y despliegue |
| Lectura del JSON, binding y Data Annotations | Navegador, interfaz de usuario y recorridos E2E |
| `[ApiController]`, respuestas 200/404/400/201 y serialización | Autenticación y servicios externos |
| Colección en memoria usada por el Service | Garantías de una implementación persistente |

Por ejemplo, el POST inválido demuestra que MVC responde 400 antes de ejecutar la Action, como en Lab07a. El POST válido y el GET de `Location` demuestran que el resultado creado puede consultarse a través del mismo pipeline. Ninguno demuestra cómo funcionaría una base de datos real.

**Integration test no significa probar absolutamente todo.** Elegimos la frontera según el comportamiento que necesitamos verificar. En otras pruebas puede tener sentido sustituir una API externa con coste o comportamiento incontrolable, conservando reales las piezas internas que se están integrando. Si reemplazamos todas esas piezas por mocks, ya no comprobamos su integración. Este lab no sustituye dependencias.

## Datos predecibles y aislamiento

El service Singleton pertenece al host, no a todo el proceso de tests. Su colección es de instancia. Cada Fact construye una factory nueva, comienza con Id 1 y la libera al terminar. La creación de otro test no puede modificar esos datos.

Compartir una factory con estado mutable requeriría controlar ese estado explícitamente. Aquí evitamos esa complejidad: cada escenario funciona individualmente o junto con los otros, sin necesitar un orden ni una reserva creada por una prueba anterior.

## Ubicación en la pirámide tradicional

```text
          /\
         /E2E\
        /-----\
       / Integr\
      /---------\
     /   Unit    \
    /_____________\
```

La pirámide es un modelo conceptual útil, no una ley universal ni una proporción fija de tests. Sugiere muchos tests unitarios para reglas específicas, tests de integración para comprobar colaboraciones y una cantidad más acotada de pruebas E2E para recorridos completos. Coste, velocidad y necesidades del sistema influyen en la elección.

Lab09a/Lab09b se ubican en Unit; Lab09c en Integr. El client HTTP no convierte automáticamente una prueba en E2E: aquí el transporte está en memoria y no participan despliegue, navegador ni infraestructura externa.
