# Repository con EF Core: cuándo aporta valor

## Objetivo

Este documento resume el criterio que venimos construyendo para usar
**Repository con EF Core** sin convertirlo en una capa ceremonial.

> **Repository aporta cuando encapsula persistencia significativa y
> expresa operaciones útiles del dominio. No hace falta agregarlo sólo
> porque "después del Service viene el Repository".**

EF Core ya cubre conceptualmente buena parte de Repository + Unit of
Work:

  Concepto                  EF Core
  ------------------------- ----------------------
  Repository de entidades   `DbSet<T>`
  Unit of Work              `DbContext`
  Consultas                 LINQ
  Agregar / eliminar        `Add()` / `Remove()`
  Confirmar cambios         `SaveChangesAsync()`
  Seguimiento               Change Tracker

## Repository que aporta poco

Un Repository genérico como:

``` csharp
public interface IRepository<T>
{
    Task<T?> GetByIdAsync(int id);
    Task<List<T>> GetAllAsync();
    Task AddAsync(T entity);
    void Update(T entity);
    void Delete(T entity);
}
```

puede terminar siendo sólo:

``` text
Service
   ↓
GenericRepository<T>
   ↓
DbSet<T>
   ↓
EF Core
```

Si únicamente traduce operaciones que `DbSet<T>` ya ofrece, la
abstracción tiene poco valor e incluso puede empobrecer EF Core
ocultando LINQ, relaciones, tracking, proyecciones y transacciones.

## Repository orientado al dominio

En Reservas cambia la situación:

``` csharp
public interface IReservaRepository
{
    Task<IReadOnlyList<Reserva>> ObtenerReservasActivasAsync(int clienteId);
    Task<IReadOnlyList<TurnoDisponible>> BuscarTurnosDisponiblesAsync(
        int servicioId, DateTime fecha);
    Task<bool> IntentarReservarCupoAsync(
        int servicioId, DateTime fecha, int cantidad);
}
```

Estos métodos expresan conceptos del problema, no copian la API de
`DbSet<Reserva>`.

## LINQ complejo no convierte automáticamente algo en Service

Es perfectamente razonable que el Repository contenga:

``` csharp
public async Task<IReadOnlyList<Reserva>> ObtenerReservasActivasAsync(int clienteId)
{
    return await _db.Reservas
        .Where(r => r.ClienteId == clienteId)
        .Where(r => r.Estado != EstadoReserva.Cancelada)
        .Where(r => r.Fecha >= DateTime.Today)
        .Include(r => r.Servicios)
        .OrderBy(r => r.Fecha)
        .ToListAsync();
}
```

El Repository puede saber **cómo obtener o persistir** los datos. El
Service debería concentrarse principalmente en **qué proceso ejecutar,
qué decisiones tomar y cómo coordinar el caso de uso**.

No es técnicamente incorrecto usar EF directamente en un Service. El
problema aparece cuando la intención del negocio queda enterrada entre
`Include`, `ThenInclude`, `Where`, `Select`, tracking y detalles de
materialización.

## Repository vs Service

La pregunta práctica es:

> **¿El método expresa una operación sobre datos persistidos o coordina
> una decisión/proceso del negocio?**

Buenos candidatos a Repository:

``` csharp
ObtenerReservasActivasAsync(...)
BuscarReservasDelClienteAsync(...)
ObtenerReservasParaFechaAsync(...)
BuscarTurnosDisponiblesAsync(...)
GuardarAsync(...)
```

Un Service, en cambio, puede coordinar:

``` text
¿el cliente puede reservar?
        ↓
¿el servicio admite la solicitud?
        ↓
¿hay disponibilidad?
        ↓
¿corresponde descuento?
        ↓
calcular seña
        ↓
crear reserva
        ↓
iniciar pago
        ↓
enviar confirmación
```

Por ejemplo:

``` text
ReservaService
     │
     ├── IReservaRepository
     ├── IClienteRepository
     ├── IPrecioService
     ├── IPagoService
     └── INotificacionService
```

## El caso interesante: `IntentarReservarCupoAsync`

Si internamente significa:

``` text
BEGIN TRANSACTION
      ↓
verificar capacidad
      ↓
insertar reserva si existe cupo
      ↓
COMMIT
```

puede ser razonable que pertenezca al Repository: encapsula una
operación atómica de persistencia y puede proteger el último cupo ante
concurrencia.

Pero si significa validar cliente + reglas comerciales + precio + cupo +
pago + notificación, ya es un proceso de aplicación y corresponde al
Service.

**El nombre del método aislado no alcanza para decidir. El contexto
importa.**

## Un Repository debería hablar el lenguaje del dominio

Preferimos:

``` csharp
await _reservas.ObtenerReservasActivasAsync(clienteId);
```

a filtrar desde el Service:

``` csharp
await _repository.FindAsync(
    r => r.ClienteId == clienteId &&
         r.Estado != EstadoReserva.Cancelada &&
         r.Fecha >= fecha);
```

No porque LINQ sea malo, sino porque el segundo caso filtra hacia el
Service conocimiento sobre cómo consultar la persistencia.

## ¿Cuándo usar `DbContext` directamente?

Para operaciones pequeñas puede ser perfectamente razonable:

``` csharp
var reserva = await _db.Reservas.FindAsync(id);
```

No hace falta crear interfaz + implementación para envolver una línea.

Podemos comenzar:

``` text
Controller
    ↓
ReservaService
    ↓
AppDbContext
    ↓
EF Core
```

y extraer cuando exista una razón:

``` text
Controller
    ↓
ReservaService
    ↓
IReservaRepository
    ↓
EfReservaRepository
    ↓
AppDbContext
```

## No es principalmente una estrategia para cambiar de ORM

Cambiar EF Core por Dapper modifica tracking, consultas, relaciones,
transacciones y actualización; Repository no vuelve ese cambio mágico.

Cambiar SQLite por PostgreSQL manteniendo EF Core ya está parcialmente
abstraído por sus providers, aunque haya aspectos específicos que
revisar.

## Criterio para nuestro proyecto Reservas

``` mermaid
flowchart TD
    A[Necesidad de acceso a datos] --> B{¿DbContext directo mantiene claro el caso de uso?}
    B -->|Sí| C[Usar DbContext / DbSet]
    B -->|No| D{¿Existe persistencia significativa con nombre propio?}
    D -->|Sí| E[Repository orientado al dominio]
    D -->|No| F[Revisar responsabilidades]
```

Indicadores favorables:

-   consultas LINQ significativas o repetidas;
-   `Include`, proyecciones o tracking contaminando el Service;
-   operaciones atómicas de persistencia;
-   consultas que merecen un nombre del dominio;
-   necesidad de concentrar optimizaciones de acceso;
-   mejora clara de la legibilidad del caso de uso.

## Conclusión

Con EF Core, Repository es **opcional, no obligatorio**.

La pregunta no es "¿una buena arquitectura tiene Repository?", sino:

> **¿Esta abstracción hace más claro el dominio y separa una
> responsabilidad real de persistencia?**

Si sólo recreamos `DbSet<T>` con `GetAll`, `GetById`, `Add`, `Update` y
`Delete`, probablemente agregamos ceremonia.

En Reservas usaremos **Repositories orientados al dominio cuando
aparezca una necesidad concreta**, manteniendo los Services enfocados en
decisiones y procesos.
