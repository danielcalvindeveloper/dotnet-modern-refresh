# `Func`, `Expression`, LINQ y Specification en EF Core

## Objetivo

La diferencia central del Lab06d es:

``` csharp
Func<Reserva, bool>
```

frente a:

``` csharp
Expression<Func<Reserva, bool>>
```

y cómo se relacionan con Specification.

> **LINQ / Expression son mecanismos para expresar y componer consultas.
> Specification es un patrón para encapsular, nombrar y reutilizar un
> criterio con significado.**

## `Func<Reserva, bool>`

``` csharp
Func<Reserva, bool> activas =
    r => r.Estado != "Cancelada";
```

Es un **delegado ejecutable**. Le damos una `Reserva` y devuelve `true`
o `false`:

``` csharp
bool resultado = activas(reserva);
```

Conceptualmente:

``` text
Reserva
   ↓
Func<Reserva, bool>
   ↓
ejecuta código .NET
   ↓
true / false
```

Es natural cuando trabajamos con objetos que ya están en memoria.

## `Expression<Func<Reserva, bool>>`

Visualmente es parecido:

``` csharp
Expression<Func<Reserva, bool>> activas =
    r => r.Estado != "Cancelada";
```

Pero conceptualmente obtenemos una **representación estructurada de la
expresión**.

Podemos imaginarla:

``` text
Lambda
  │
  └── NotEqual
       ├── Member: Estado
       └── Constant: "Cancelada"
```

Es código representado como datos. Otra biblioteca puede inspeccionarlo.

## Por qué es fundamental para EF Core

``` csharp
Expression<Func<Reserva, bool>> activas =
    r => r.Estado != "Cancelada";

var query = _db.Reservas.Where(activas);
```

EF Core puede inspeccionar ese árbol y traducirlo:

``` mermaid
flowchart LR
    A["r => r.Estado != Cancelada"] --> B[Expression Tree]
    B --> C[EF Core]
    C --> D[Provider]
    D --> E[SQL]
    E --> F[Base de datos]
```

Conceptualmente termina produciendo algo equivalente a:

``` sql
WHERE Estado <> 'Cancelada'
```

## `IQueryable<T>` y ejecución diferida

``` csharp
IQueryable<Reserva> query = _db.Reservas;

query = query.Where(r => r.Estado == "Pendiente");
query = query.Where(r => r.Fecha >= desde);
query = query.OrderBy(r => r.Fecha);
```

Estamos componiendo una consulta, no ejecutando tres consultas SQL.

La materialización ocurre al hacer, por ejemplo:

``` csharp
var reservas = await query.ToListAsync();
```

El recorrido conceptual es:

``` text
IQueryable
    ↓
Expression Tree
    ↓
EF Core
    ↓
SQL
    ↓
Base de datos
    ↓
filas
    ↓
objetos Reserva
```

## Contraste con datos ya materializados

Esto:

``` csharp
var reservas = await _db.Reservas.ToListAsync();

var pendientes = reservas
    .Where(r => r.Estado == "Pendiente");
```

primero trae los datos. El `Where` posterior filtra objetos en memoria.

En cambio:

``` csharp
var pendientes = await _db.Reservas
    .Where(r => r.Estado == "Pendiente")
    .ToListAsync();
```

permite que EF traduzca el criterio y que el filtrado ocurra en la base.

## Entonces, ¿para qué sirve Specification?

LINQ directo:

``` csharp
_db.Reservas
    .Where(r => r.Estado != "Cancelada");
```

Podemos extraer el criterio:

``` csharp
Expression<Func<Reserva, bool>> activas =
    r => r.Estado != "Cancelada";
```

Eso ya permite reutilización.

Specification agrega principalmente **estructura, nombre e intención**:

``` csharp
public interface ISpecification<T>
{
    Expression<Func<T, bool>> Criteria { get; }
}
```

``` csharp
public sealed class ReservasActivasSpecification
    : ISpecification<Reserva>
{
    public Expression<Func<Reserva, bool>> Criteria =>
        r => r.Estado != "Cancelada";
}
```

Uso:

``` csharp
var spec = new ReservasActivasSpecification();

var reservas = await _db.Reservas
    .Where(spec.Criteria)
    .ToListAsync();
```

## Specification no reemplaza LINQ

Nuestra Specification contiene precisamente una:

``` csharp
Expression<Func<Reserva, bool>>
```

que EF utiliza dentro de una consulta LINQ.

``` text
ReservasActivasSpecification
          ↓
da nombre a un concepto
          ↓
Expression<Func<Reserva,bool>>
          ↓
representa el criterio
          ↓
LINQ / IQueryable
          ↓
compone la consulta
          ↓
EF Core
          ↓
SQL
```

Specification está en otro nivel de abstracción.

## Tres niveles posibles

### LINQ directo

``` csharp
var reservas = await _db.Reservas
    .Where(r => r.Estado != "Cancelada")
    .ToListAsync();
```

Ideal cuando el criterio es simple y local.

### Expression reutilizable

``` csharp
Expression<Func<Reserva, bool>> activas =
    r => r.Estado != "Cancelada";

var reservas = await _db.Reservas
    .Where(activas)
    .ToListAsync();
```

Útil cuando queremos reutilizar el criterio manteniéndolo traducible por
EF Core.

### Specification

``` csharp
var spec = new ReservasActivasSpecification();

var reservas = await _db.Reservas
    .Where(spec.Criteria)
    .ToListAsync();
```

Aporta un concepto explícito: **ReservasActivas**.

## La ventaja semántica

Comparemos:

``` csharp
var reservas = await _db.Reservas
    .Where(r =>
        r.Estado != "Cancelada" &&
        r.Fecha >= hoy &&
        r.Cliente.Activo)
    .ToListAsync();
```

con:

``` csharp
var spec = new ReservasActivasSpecification(hoy);
```

La primera explica **cómo** está formado el criterio.

La segunda puede expresar **qué significa** ese criterio para el
dominio.

Specification empieza a ser interesante cuando la definición:

-   se repite;
-   tiene importancia de negocio;
-   evoluciona;
-   necesita ser probada aisladamente;
-   merece una identidad conceptual.

## ¿Specification siempre conviene?

No.

Esto:

``` csharp
_db.Reservas.Where(r => r.Id == id)
```

probablemente no necesita:

``` csharp
ReservaPorIdSpecification
```

Crear una Specification para cada `Where` trivial sólo agrega ceremonia.

La pregunta útil es:

> **¿Darle nombre y encapsular este criterio mejora realmente la
> aplicación?**

## Relación con Repository

Podríamos terminar teniendo:

``` csharp
var spec = new ReservasActivasSpecification(hoy);
var reservas = await _reservas.BuscarAsync(spec);
```

Conceptualmente:

``` text
Service
   ↓
Specification
   │ describe el criterio
   ↓
Repository
   │ resuelve la persistencia
   ↓
EF Core / LINQ
   ↓
SQL
```

Pero no estamos obligados a combinar ambos patrones.

Un Repository orientado al dominio también podría ofrecer directamente:

``` csharp
await _reservas.ObtenerReservasActivasAsync(clienteId);
```

y encapsular internamente el LINQ. La decisión depende de si hacer
explícita la Specification aporta valor.

## Resumen mental

  -----------------------------------------------------------------------
  Concepto                            Función principal
  ----------------------------------- -----------------------------------
  `Func<Reserva,bool>`                Código ejecutable sobre una
                                      `Reserva`

  `Expression<Func<Reserva,bool>>`    Representación inspeccionable del
                                      código

  LINQ + `IQueryable`                 Composición de una consulta
                                      traducible

  EF Core                             Traducción y ejecución contra el
                                      provider

  Specification                       Nombre y encapsulación de un
                                      criterio
  -----------------------------------------------------------------------

La frase para recordar:

> **`Func` ejecuta; `Expression<Func<...>>` describe; LINQ compone; EF
> traduce; Specification da nombre y reutiliza una intención.**

## Conclusión

No debemos preguntar **"¿LINQ o Specification?"**.

LINQ y Expression Trees proporcionan el mecanismo técnico que EF Core
utiliza para construir consultas. Specification aparece en otro nivel:
convierte, cuando vale la pena, una expresión técnica en un concepto
explícito y reutilizable del dominio.

La pregunta correcta es:

> **¿Este criterio LINQ merece ser encapsulado, nombrado y reutilizado
> como un concepto?**

Si sí, Specification puede aportar valor. Si la consulta es simple y
local, LINQ directo suele ser suficiente.
